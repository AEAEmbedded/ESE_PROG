**HAN University of Applied Sciences - Embedded Systems Engineering - Programming 6**

| Competency | Advanced | Proficient | Emerging | Novice |
|---|---|---|---|---|
| **Analyze: Problem** | The problem statement is linked to a concrete training situation at the Wilhelmina Children's Hospital (WKZ). User stories cover all actors. The solution was validated with a WKZ or nursing expert and the feedback was processed. | The problem statement is linked to a training situation at WKZ. User stories cover the main actors. Not yet validated with an expert, or feedback only partly processed. | A problem statement is given, but it is generic or only partly linked to WKZ. User stories are incomplete. | No problem statement, or not linked to a realistic problem. No real-world examples. |
| **Requirements** | All requirements are SMART. Every requirement is classified with FURPS+, prioritized with MoSCoW and traceable to a user story. | Most requirements are SMART. FURPS+ and MoSCoW are applied to most requirements. | Few requirements are SMART. FURPS+ or MoSCoW is applied incompletely or incorrectly. | No SMART requirements. No FURPS+ and/or no MoSCoW. |
| **Design** | The design follows SOLID throughout. Components and interfaces are explicit, design choices are justified, and the proof-of-concept follows the design. | The design follows SOLID in most parts. Some details are missing. The proof-of-concept largely follows the design. | A basic design with the key elements, but SOLID is hardly visible, or design and code diverge. | No design, or key elements needed for the implementation are missing. |
| **Functional** | A use case diagram with actors, subsystems, include and extend. The main use cases are fully elaborated in text and consistent with the requirements. | Use case diagram and use case texts are present, with a few inconsistencies or missing details. | Use cases are present, but incomplete or with many inconsistencies. | No use cases and/or no elaboration. |
| **Technical** | At least three types of technical design (e.g. Class, Sequence, State), in correct UML and consistent with the code. | At least two types of technical design, mostly correct and consistent with the code. | At least one type of technical design, or diagrams with substantial errors or inconsistencies. | No adequate technical design. |
| **Manage: Code Management** | A shared repository with small commits and clear commit messages throughout the assignment. Feature branches with pull requests, every pull request reviewed by a teammate. | Regular commits with mostly clear messages. Some pull requests and reviews. | Git is used at a basic level: few, large commits, unclear messages, no pull requests. | No Git, or code shared in other ways. |
| **Control: Testing** | Automated unit tests for the core logic (e.g. transitions, timing, early warning score) and an integration test via MQTT. Tests run reproducibly and results are reported. | Unit tests for the main parts of the core logic and documented manual integration tests. | Some tests, mainly manual and undocumented. The core logic is largely untested. | No or virtually no testing. |
| **Realization: Proof-of-Concept** | The proof-of-concept runs a scenario end to end (editor, engine, SimDevice, debrief), works reliably in a live demo and proves the case. | The proof-of-concept runs end to end, with minor issues or workarounds. | Parts work separately, but not end to end. | No working proof-of-concept, or not relevant for the problem. |
| **Realization: Application of OO principles** | Classes, encapsulation, inheritance, abstract base classes and interfaces are each applied where they fit, and the choices are justified. | Abstract base classes or interfaces are applied correctly, in addition to classes and encapsulation. | The basic OO principles are applied: classes and encapsulation. | No OO principles are applied. |
| **Good programming: SOLID / DRY / KISS** | SOLID, DRY and KISS are applied consistently. Coding guidelines and naming conventions are followed, Doxygen documentation without unnecessary comments. A new team member can read the code without help. | Mostly applied, with some duplication or overly long functions. Guidelines are mostly followed. | Applied in parts only: noticeable duplication, unclear names or inconsistent style. | Not applied: the code is hard to read and no guidelines are followed. |
| **Professionalize: Reflection on your work** | A well-founded advice to WKZ, based on the use cases and the results of the proof-of-concept, including its limitations. Presented convincingly in a presentation, report or video. | The advice is based on the use cases and the proof-of-concept, but the argumentation has gaps. | The advice is hardly based on the use cases or the proof-of-concept, or it is not convincing. | No advice. |
| **Professionalize: personal level** | Keeps agreements, contributes visibly (commits, tasks) and communicates proactively with team and teacher. Explains and changes own code in the final interview without help. | Keeps most agreements and communicates reasonably. Explains own code with little help. | Regularly misses agreements or communicates late. Explains own code only with help. | Little contribution and poor communication. Cannot explain own code. |

**Note:** make sure all files and documents are in a readable format without the need for additional installers (apart from any basic IDE and/or image viewer): diagrams should be PNG/PDF, source in `.c(pp)`/`.h(pp)`/`.py`/other text formats. In case you want to demo something hand it in as a video. Documentation in PDF format.

**Changes from v1.5:** level descriptions made observable (what the assessor can check in the hand-in), no dependence on the enthusiasm of third parties, no overlap between levels, and the personal level linked to the final interview.
